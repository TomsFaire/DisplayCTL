# Claude Code Handoff: Display Power Scheduler (Q-SYS replacement pilot)

## 1. Goal

Build a small, self-hosted service that replaces the Q-SYS Core's **scheduled conference-room display power control**. It runs on the existing always-on "eng" Mac mini in each office. It must port to Linux (Debian/RHEL/Raspberry Pi OS) later with no code changes, only a different service-manager file.

One instance per office. Each instance controls about 25 displays on its local network.

**Scope:** Display power on/off, power status, schedules, manual overrides, logs and a web UI.
**Out of scope:** Audio DSP, video routing, input switching beyond what's needed for power, and multi-office central management.

## 2. Target hardware

| Family | Control path | Protocol (verify against each model's manual) |
|---|---|---|
| Samsung QM-series (e.g. QM55C, QM65B) | Native IP **or** RS-232 through a Global Caché adapter | Samsung MDC. Default TCP 1515. Binary frames |
| Samsung QB-series (e.g. QB65B) | Same as QM | Samsung MDC |
| LG digital signage (model TBC) | Native IP **or** RS-232 through a Global Caché adapter | LG RS-232C/IP ASCII ("ka" commands). Commonly TCP 9761. Wake-on-LAN may be required for power-on |
| Global Caché (iTach IP2SL, Flex, GC-100) | Raw TCP serial tunnel | Port 4999 for serial port 1 (5000 for port 2 on 2-port units). Configure baud and framing on the adapter |

**Important:** The protocol details below are a starting point only. Every driver must be validated on a real device before the pilot. Treat any constant as configurable where practical.

### 2.1 Samsung MDC (starting point)

- Frame: `0xAA, CMD, ID, LEN, DATA..., CHECKSUM`. The checksum is the sum of all bytes after `0xAA`, mod 256.
- Power command `0x11`: data `0x01` = on, `0x00` = off. Status query = the same command with `LEN=0`.
- ACK: `0xAA 0xFF ID LEN 'A'(0x41) R-CMD VALUE... CHK`. NAK uses `'N'(0x4E)`.
- Display ID is per-display configuration (often 0 or 1). Do not hardcode it.
- **Power-on over IP requires "Network Standby" (or equivalent) enabled on the display.** Document this in the README as a commissioning step.
- Newer Samsung firmware may enforce **secured MDC (TLS + PIN)** on port 1515. Design the transport so a driver can choose plain TCP or TLS, plus an optional PIN handshake. Implement plain TCP first. Leave a clearly marked, tested extension point for TLS/PIN, and flag it if the pilot displays require it.
- RS-232 via Global Caché: same frames; typically 9600 8N1. Confirm per model.

### 2.2 LG signage (starting point)

- ASCII, CR-terminated: `ka <setID> <data>\r`.
  - On: `ka 01 01`. Off: `ka 01 00`. Status: `ka 01 ff`.
- Response like `a 01 OK01x` or `a 01 NG..x`. Parse OK/NG and the value.
- Set ID is per-display configuration. ID `00` may broadcast on some models. Don't use broadcast by default.
- Many LG panels **do not accept TCP power-on when off**. Support a per-display `wake_method: wol` that sends a Wake-on-LAN magic packet (UDP 9, broadcast, configurable) to the display MAC, then waits and polls status over TCP.
- The exact model is TBC. Keep the driver tolerant, and log raw request and response bytes at debug level.

### 2.3 Global Caché transport

- Open TCP to `adapter_ip:4999` (or the configured port), write the raw display bytes and read the response with a timeout.
- Adapters may allow only **one client connection at a time**. Connect, send, read and close. Never hold the socket open. Serialize all access per adapter with a lock.
- No Global Caché command syntax is needed for serial pass-through.

## 3. Architecture

```
config.yaml ──► Core service (Python, asyncio)
                 ├─ Scheduler (tz-aware, reconciling)
                 ├─ Device registry ─► Drivers (samsung_mdc, lg_signage)
                 │                       └─ Transports (tcp, tls, globalcache_serial, wol)
                 ├─ State + audit log (SQLite)
                 └─ Web UI + JSON API (FastAPI, server-rendered HTML + HTMX)
```

### Stack (prefer boring and portable)

- Python 3.11+ (use `zoneinfo`). Manage with `uv` or a plain venv. Don't rely on macOS system Python.
- FastAPI + Uvicorn, Jinja2 templates and HTMX. No Node build step, no SPA.
- SQLite via the standard library `sqlite3` (or SQLAlchemy Core if justified).
- PyYAML + Pydantic for config validation.
- No platform-specific APIs in application code. All OS differences live in `deploy/macos/` and `deploy/linux/`.

## 4. Configuration (`config.yaml`)

The web UI **port and bind address must come from the config**, overridable by CLI flag or env var for troubleshooting: `--port`, `DPS_PORT`. Example:

```yaml
site:
  name: "NYC"
  timezone: "America/New_York"

web:
  bind: "0.0.0.0"        # use 127.0.0.1 to restrict to local access
  port: 8000             # change freely for troubleshooting
  auth:
    username: "avadmin"
    password_hash: "<argon2/bcrypt hash>"   # generated by CLI; never plaintext
  # optional: allowed_cidrs: ["10.20.0.0/16"]

defaults:
  command_timeout_s: 5
  retries: 3
  retry_backoff_s: [2, 5, 10]
  max_concurrency: 5      # parallel devices; per-adapter calls are serialized anyway
  verify_after_s: 20      # poll status after power commands

schedules:
  - name: "Weekday hours"
    days: [mon, tue, wed, thu, fri, sat, sun]
    on: "06:00"
    off: "20:00"

displays:
  - id: nyc-conf-hudson
    name: "Hudson (Conf 4A)"
    room: "4A"
    driver: samsung_mdc
    transport: { type: tcp, host: 10.20.70.31, port: 1515 }
    display_id: 1
    schedule: "Weekday hours"
    enabled: true

  - id: nyc-conf-east
    name: "East Room"
    driver: samsung_mdc
    transport: { type: globalcache_serial, host: 10.20.70.50, port: 4999 }
    display_id: 0
    schedule: "Weekday hours"

  - id: nyc-lobby-lg
    name: "Lobby LG"
    driver: lg_signage
    transport: { type: tcp, host: 10.20.70.40, port: 9761 }
    set_id: 1
    wake: { method: wol, mac: "AA:BB:CC:DD:EE:FF", broadcast: 10.20.70.255 }
    schedule: "Weekday hours"
```

Requirements:

- Validate the config on startup and in `dps check-config`. Fail fast with clear errors: unknown driver, duplicate ID, bad time zone, missing schedule.
- Support per-display schedules, multiple schedules, and an `exceptions` list (dates with all-off or custom hours, e.g. holidays).
- Keep secrets (UI password hash, any MDC PIN) out of git. Allow them via env var or a separate `secrets.yaml` with restrictive file permissions.
- Hot-reload the config from the UI ("Reload config"), or restart cleanly. Don't silently half-apply a bad config.

## 5. Scheduling behavior (critical)

- **Reconciling, not fire-and-forget.** Every minute, compute each display's *intended* state from its schedule, exceptions and any active override. Act only on transitions, and on startup.
- **On startup** (e.g. after the weekly Mac mini reboot), apply the current intended state once. Example: if the service boots at 07:10, displays should be ON. Don't replay a missed 20:00 OFF the next morning.
- Use the site time zone via `zoneinfo`. Handle DST: a skipped local time still fires on that day once the time has passed; a repeated hour fires once. Write unit tests for both.
- **Manual override** from the UI: "Force on/off until next scheduled change" (default) or "for N hours". Overrides persist in SQLite across restarts.
- Send explicit on/off commands. Never toggle.
- **Retries:** bounded, with backoff. After the final failure, mark the display `FAILED` and surface it prominently in the UI.
- If status isn't supported or the display doesn't answer, record `COMMAND_SENT_UNVERIFIED` rather than claiming success.
- **Idempotent:** Re-sending ON to an ON display is harmless. Optionally skip it if a fresh status confirms the state.
- Allow concurrency across devices, up to `max_concurrency`. Serialize per Global Caché adapter and per display.

## 6. Web UI

Server-rendered, works without JavaScript where possible. HTMX adds partial refresh.

- **Dashboard:** a table of displays with room, model/driver, transport, last known power state, last action, result, time and next scheduled action. Color coding: on / off / unverified / failed / disabled.
- **Per-display actions:** Power On, Power Off, Query Status, plus override with a duration. Add a "Test connection" action that shows raw TX/RX bytes (hex for MDC, ASCII for LG), for troubleshooting.
- **Bulk actions:** All On, All Off and Query All, each with a confirmation step.
- **Schedules page:** read-only view of the effective schedules, today's and tomorrow's planned actions, and active overrides with a Cancel button. Editing schedules in the UI is optional in v1; editing YAML is acceptable.
- **Log page:** filterable audit log covering time, actor (scheduler or user), display, action, result and error.
- **Health:** `GET /healthz` returns a JSON summary (scheduler alive, last tick, failed count) for monitoring. This endpoint is unauthenticated, but must contain no secrets.
- **Security:**
  - HTTP Basic or session login using the configured hash.
  - CSRF protection on state-changing POSTs.
  - Optional `allowed_cidrs`.
  - No unauthenticated control endpoints.
  - Document putting TLS in front (or using Caddy) if needed. Plain HTTP on the internal network is acceptable for the pilot.
- **JSON API** mirroring the UI actions (`/api/displays`, `/api/displays/{id}/power`, etc.) for future automation.

## 8. Deployment

### macOS (pilot: existing "eng" Mac mini, reboots weekly)

- Install to `/opt/dps` (app plus venv). Put the config in `/usr/local/etc/dps/` and logs/DB in `/usr/local/var/dps/` (or another documented path).
- Use a **LaunchDaemon** (`/Library/LaunchDaemons/com.faire.dps.plist`), not a LaunchAgent, so it runs without a user login. Set `RunAtLoad=true` and `KeepAlive=true`, run as a dedicated non-admin user where feasible, and set stdout/stderr paths.
- `deploy/macos/install.sh` and `uninstall.sh` must be idempotent.
- **README notes to verify during the pilot:**
  - The macOS Application Firewall may prompt or block inbound connections to the UI port. Document how to allow it.
  - Check whether macOS Local Network privacy affects the daemon. Test outbound connections to displays after a reboot, with no user logged in.
  - Confirm the weekly reboot time doesn't overlap 06:00 or 20:00. Startup reconciliation covers it either way.
  - Ensure the clock syncs via NTP.
- Log rotation must be bounded (size-based rotating handler in the app). Don't rely on newsyslog.

### Linux (later)

- `deploy/linux/dps.service` (systemd): `Restart=on-failure`, dedicated `dps` user, `ProtectSystem=strict`, `ReadWritePaths` for data, and `After=network-online.target`.
- Paths: `/opt/dps`, `/etc/dps`, `/var/lib/dps`.
- `deploy/linux/install.sh`. It must work on Debian 12, RHEL 9 and Raspberry Pi OS (arm64).
- Optional: a Dockerfile. Note that Wake-on-LAN broadcasts need host networking.

## 10. Driver interface

```python
class DisplayDriver(Protocol):
    async def power_on(self) -> CommandResult: ...
    async def power_off(self) -> CommandResult: ...
    async def get_power(self) -> PowerState   # ON | OFF | UNKNOWN
    capabilities: set[str]                    # e.g. {"status", "wol"}
```

`CommandResult` contains: success, verified, raw TX/RX bytes, latency, error.

Adding a new display family should take only one new driver file plus registration.

## 11. Testing and acceptance

**Automated** (`pytest`, runs on macOS and Linux CI):

- MDC frame building, checksums, and ACK/NAK parsing, including partial reads and garbage bytes.
- LG command formatting and OK/NG parsing.
- Scheduler: normal day, DST spring-forward and fall-back, exceptions, startup at various times, override expiry and persistence across restart.
- Fake TCP servers emulating MDC, LG and a single-connection Global Caché adapter. Include timeout, refused and slow-response scenarios.
- Web: auth required, CSRF enforced, port/bind honored from config and CLI override.

**Pilot acceptance**, on real hardware in one office:

1. One Samsung QM/QB over native IP, one Samsung via Global Caché, and one LG. Each must turn on from standby, turn off and report status.
2. The full office (~25 displays) completes the 06:00 ON and 20:00 OFF within 2 minutes, with results logged.
3. Reboot the Mac mini mid-day. The service starts with no login, reconciles state and the UI is reachable on the configured port.
4. Unplug one display's network. It retries, is marked FAILED and the others are unaffected.
5. Change the port in the config and restart. The UI moves to the new port.
6. The Q-SYS schedule is disabled for the pilot rooms only, with a rollback documented.

## 13. Working instructions for Claude Code

- Start with `config.py`, drivers/transports with fake-server tests, then the scheduler with DST tests, then the CLI, web UI and deployment scripts.
- Keep dependencies minimal. Pin versions in `pyproject.toml`.
- Never send commands to real devices from tests.
- When protocol details are uncertain, implement the most common variant. Make it configurable, add a `# VERIFY:` comment and list it in the README's "Commissioning checklist".
- Deliver a README that a non-developer AV/IT tech can follow to install, add a display and troubleshoot.
